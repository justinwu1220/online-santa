# 兒童隱私保護規範

本平台處理的是**未成年人**的資料。孩子沒有能力評估自己的資訊被公開後會有什麼後果，
這個責任落在機構與平台身上。以下不是建議，是這個系統運作的前提。

---

## 一、系統層級的保護

這些保護不依賴任何人記得遵守——它們是結構性的。

### 資料庫 schema 沒有可識別欄位

`wishes` 表**不存在**姓名、生日、住址、學校、身分證號、孩童照片等欄位。
只有三個描述孩子的欄位：

| 欄位 | 內容 | 為什麼安全 |
|---|---|---|
| `child_alias` | 暱稱（「小星」） | 非真實姓名 |
| `age_range` | 年齡**區間**（`AGE_7_9`） | 不是生日，也不是確切歲數 |
| `interests` | 興趣描述（「喜歡畫畫和恐龍」） | 不具識別性 |

想外洩也沒有地方可存。這比寫在規範文件上的「請勿填寫真實姓名」可靠得多。

### 檔案依敏感度分放兩個 bucket

| Bucket | 內容 | 存取方式 |
|---|---|---|
| **公開** | 禮物示意圖、願望信件照片 | 固定網址，公開可讀 |
| **私密** | 寄送證明、送禮回饋照片、機構申請文件 | 限時簽章網址（10 分鐘），過期失效 |

分成兩個 bucket 而不是同一個 bucket 靠程式判斷：設錯權限的後果是孩童照片外流，
這件事不該只靠應用層的 `if` 把關。

「公開」裡的兩種用途（禮物示意圖、願望信件照片）都是**刻意的既有例外**，
不是漏加判斷的結果——理由與各自的把關方式見第二節。

### 回應型別分離

公開端點回傳 `WishPublicView`，機構端點回傳 `WishOrgView`，是兩個獨立的 Java 型別，
而非同一個 DTO 再視情況清空欄位。後者只要有人漏判一次就會外洩；型別分離讓
「公開端點不可能回傳內部欄位」在編譯期就成立。

### 認領附件的可見範圍

寄送證明與回饋照片**只有兩方看得到**：該筆認領的捐贈者，以及願望所屬機構。
其他捐贈者、其他機構、未登入者一律 404。

### 捐贈者的真實姓名

認領者註冊時要填「真實姓名」（`users.name`），用於捐贈收據與向衛福部申報的徵信名冊。
它與「顯示名稱」（`users.display_name`）是兩個獨立的欄位：

| 欄位 | 誰看得到 | 用途 |
|---|---|---|
| `display_name` | 願望所屬機構、管理員（以 `donorName` 顯示） | 機構與孩子看到的名字，可以用暱稱 |
| `name` | **只有本人**，在自己的個人資料頁 | 收據與徵信名冊，不會顯示在網站上 |

- `name` 目前只出現在 `UserProfileView` 一個回應型別裡（本人的個人檔案端點）。
  機構端與管理端的回應型別（`ClaimOrgView`、`AdminClaimView` 等）沒有這個欄位，
  所以不是靠「記得不要回傳」，而是型別上就拿不到。
- 不想具名的人可以按「使用善心人士名義」，欄位會填入「善心人士」。這是使用者自己
  選擇的值，系統不會替他匿名化，也不會自行判斷這個字串。
- 欄位在資料庫允許 NULL：既有帳號、機構成員與管理員沒有這個資料，只有註冊表單
  對新的認領者要求必填。個人資料頁可以補填或修改。
- 捐贈收據本身的資料（身分證字號、地址等）另有一節，見下面的「捐贈收據資料」。
  日後若要產生徵信名冊，同樣應由專用的管理端點讀取，並先在這裡補一段說明
  誰能匯出、匯出的資料如何保管，不要為了方便直接加進現有的機構端或管理端回應。

### 參與須知的同意紀錄

認領者註冊時要先閱讀並同意《認領者參與須知》。每次同意在 `terms_consents` 新增一列（使用者、須知種類、**版本**、同意時間），只增不改——須知改版後使用者要重新同意，舊版本的同意紀錄保留，才查得到當時同意的是哪個版本。目前版本由後端設定（`app.terms.donor-version`）決定；最近一次同意的版本與目前版本不同，就視為尚未同意目前版本，認領前會被擋下並要求重新同意。這份紀錄只有使用者本人透過 `/api/me/terms` 讀得到，機構端與管理端目前沒有對外的端點。

### 捐贈收據資料

認領者回報寄送時可以選擇申請捐贈收據（預設關閉）。申請時要填：姓名或公司名稱、
身分證字號或統一編號、電子信箱、收件地址，並上傳紙本或電子發票證明。這是系統裡
**最敏感的個資**，保護方式如下：

| 項目 | 做法 |
|---|---|
| 誰看得到 | **只有平台管理員**。機構、其他捐贈者都看不到，連「有沒有申請」機構端的回應型別（`ClaimOrgView`）都沒有這個旗標 |
| 資料放哪 | 獨立的 `claim_receipts` 表，不在 `claims` 上。機構端與捐贈者端的回應都從 `Claim` 實體轉出，資料不在那個實體上就帶不出去 |
| 身分證字號／統一編號 | **應用層加密**（AES-256-GCM，每次隨機 IV）後存放，資料庫與備份外洩也看不到明文。金鑰由環境變數 `RECEIPT_ENCRYPTION_KEY` 提供，**金鑰遺失就無法解密**，要另外備份 |
| 發票證明檔案 | 私密 bucket（`receipt-proofs/`），限時簽章網址；刻意不在 `claimAttachments`（捐贈者與機構共用的附件清單）裡，只有管理端專用方法讀得到。可用 PDF |
| 管理員查閱 | 專用端點 `GET /api/admin/claims/{id}/receipt`，每次讀取寫入 `VIEW_CLAIM_RECEIPT` 稽核；稽核內容只記機構與願望，**不記證號** |
| 管理員列表 | 只有 `receiptRequested` 旗標（用來篩選「需要捐贈收據」），列表不含任何收據內容；詳情頁要按「載入捐贈收據資料」才讀取 |
| 捐贈者自己 | 回報寄送後只看得到「已申請」，看不到自己填的內容，也不能修改；送出前有二次確認。需要更正請聯繫 onlinesanta2026@gmail.com，由管理員處理 |
| 刪除 | 捐贈者送出後不能自行刪除發票證明，只有管理員能刪 |

- 身分證字號只在 `ClaimReceiptService` 加解密，實體與其他層碰不到明文。
- 前端的管理員詳情頁不把收據資料留在查詢快取（`gcTime: 0`），離開頁面再回來要重新載入，
  也會重新寫一筆稽核。
- 不得把這些欄位加進任何現有的回應型別，也不要為了列表好看把證號顯示在列表上。

## 二、機構上架願望時的規範

系統擋不掉的部分，需要機構配合。

### 禁止

- ❌ 在任何欄位填寫孩子的**真實姓名**（含小名以外的名字、姓氏）
- ❌ 填寫**確切生日**或足以推算生日的敘述
- ❌ 提及**學校名稱、班級、安置機構的門牌**
- ❌ 上傳**孩子的清晰正面照**作為示意圖
- ❌ 描述**特殊身體特徵、疾病、家庭變故細節**——這些組合起來足以識別特定孩子

### 建議

| 不要這樣寫 | 改成這樣 |
|---|---|
| 「陳小明，10 歲，中正國小四年二班」 | 「小明，10-12 歲」 |
| 「爸爸入獄後由阿嬤照顧」 | （不要提；與禮物無關） |
| 「有先天性心臟病，行動不便」 | 「喜歡安靜的室內活動」 |
| 上傳孩子拿著願望清單的照片 | 上傳禮物本身的示意圖 |

**判斷原則**：如果一個陌生人拿著這則願望的內容，有可能在現實中認出這個孩子，
那就寫得太多了。

### 願望信件照片——第二個公開 bucket 例外

機構可以上傳孩子手寫的感謝卡／願望信照片（`WISH_LETTER`），顯示在願望牆的願望
詳情頁上，讓捐贈者看到孩子的回應。這跟本文件開頭「可能含孩童影像一律私密」的
原則字面上衝突，但沿用的是 `WISH_IMAGE`（禮物示意圖）同一套既有例外模式：

- **公開 bucket，固定網址**——因為要顯示在公開的願望詳情頁，不能用會過期的
  簽章網址。
- **換成上傳介面強制顯示提醒**，取代系統層級的存取限制：機構後台上傳信件照片
  的區塊旁邊固定顯示「請拍卡片內容，避免拍到孩子的臉部或完整姓名」。
- 判斷原則與第二節相同：陌生人看了這張照片，有沒有可能認出這個孩子。拍信件
  內容本身（字跡、畫作、文字）幾乎不會踩到這條線；拍到孩子正臉或完整姓名的
  落款則會。

這是**第二個**被記錄在案的公開例外，不是悄悄打開的漏洞——新增任何公開 bucket
用途前，請先在這裡補一段說明，而不是只改程式碼。

## 三、送禮回饋照片的規範

機構收到禮物後回傳照片給捐贈者，是這個平台最溫暖的一環，也是風險最高的一環。

### 必須

- ✅ 拍**禮物本身**、拆封的手、背影、局部（如手中的畫筆）
- ✅ 若要拍到孩子，**必須取得監護人或安置機構的書面同意**
- ✅ 上傳前確認背景沒有洩漏地點（門牌、招牌、制服上的校名）

### 提醒捐贈者

回饋照片是**限時簽章網址**，會過期。這是刻意的設計：捐贈者可以看，但不便於長期
保存或轉傳。系統無法阻止截圖，因此照片內容本身就不該是需要嚴格保密的東西。

## 四、技術限制

| 項目 | 限制 | 原因 |
|---|---|---|
| 檔案型別 | 僅 JPEG / PNG / WebP（機構申請文件與捐贈收據的發票證明額外開放 PDF） | **不支援 SVG**——它可以夾帶 JavaScript |
| 檔案大小 | 5 MB | 避免濫用儲存空間 |
| 上傳網址有效期 | 15 分鐘 | 縮小網址外流的影響範圍 |
| 讀取網址有效期 | 10 分鐘 | 同上 |
| 型別驗證 | 以**儲存端實際查詢**為準 | 前端宣稱的型別與大小不可信 |

> 注意：目前只驗證 MIME 型別，未檢查檔案內容的 magic bytes。想上傳偽裝成 JPEG
> 的檔案在技術上可行。由於檔案只會被當作圖片顯示、且存在獨立的 bucket，
> 風險有限；若日後開放更多檔案型別，應補上內容驗證。

## 五、發生疑似外洩時

1. 立即在管理後台將該機構設為 `SUSPENDED`，停止其上架能力
2. 從 Cloud Storage 刪除相關物件（簽章網址最長 10 分鐘後失效，但已下載的檔案無法收回）
3. 通知受影響的孩子的監護人與安置機構
4. 記錄事件經過，檢討是哪一層防線失效

---

## 六、給開發者

新增任何欄位或端點前，先問三個問題：

1. **這個欄位會被存在哪裡？** 若涉及孩童，能不能用區間、代號或不存來取代？
2. **誰看得到？** 公開端點的回應型別裡有沒有混進內部欄位？
3. **檔案放哪個 bucket？** 只要可能含孩童影像或捐贈者個資，一律私密——除非像
   `WISH_IMAGE`／`WISH_LETTER` 這樣是經過評估、記錄在案的刻意例外（見第二節），
   且用介面提醒取代存取限制來把關。新增例外前請先補一段說明在這裡，不要只改
   程式碼。

`AttachmentApiIT` 與 `SchemaMigrationIT` 中有幾則測試專門守著這些界線
（例如斷言 `wishes` 表不存在 `child_name`、`birth_date`、`photo_url` 等欄位）。
它們失敗時，代表有人正在拆掉一道防線——請不要只是把測試改掉。
