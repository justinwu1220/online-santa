# 專案體檢報告：功能總結、缺口與上線 UX 預判

> 2026-09-01 · fable-brain · 基於全程式碼庫盤點（不含 .claude/worktrees），檔案行號為當日 main（7fa78df）

## 1. 現有系統功能總結

一套程式碼、三個使用者感受上獨立的平台，身分系統共用（Firebase Auth + JIT provisioning，DONOR/ORG_MEMBER/ADMIN 三角色）。

### 大眾平台（願望牆，深色玻璃主題）

- **瀏覽**：願望牆卡片列表，類別/年齡/價格帶三種篩選（選項由後端動態提供）、分頁；願望詳情頁含麵包屑、圖片或 emoji fallback、404 專屬畫面
- **認領**：完整的權限階梯（已被認領→未登入→信箱未驗證→角色不符→可認領）、選填 500 字給孩子的話；併發搶認領有樂觀鎖 + 部分唯一索引保護，撞車時顯示「手慢了一步 🎄」並刷新
- **帳號**：密碼註冊（含確認密碼）/登入/Google 登入/忘記密碼（防帳號枚舉文案）/信箱驗證橫幅；15 種 Firebase 錯誤碼有中文對應；個人檔案頁（用戶名稱、電話、驗證狀態、密碼重設）
- **我的認領**：年度篩選 + 年度小結卡（cohort 制）、未讀訊息數、逾期倒數；認領詳情含收件地址、回報寄送（物流商+單號）、寄送證明上傳（三段式 signed URL）、機構回饋照片、站內對話、兩段式確認的取消流程、時間軸

### 機構後台（亮色 console）

- **申請流程**：兩步驟（帳號→申請表）、sessionStorage 草稿、信箱驗證閘門、被拒後可重送
- **願望管理**：CRUD（草稿才能刪）、上架/下架、狀態篩選（URL 同步）、示意圖上傳（feature flag，預設關）
- **認領管理**：確認收到/完成/釋回（附原因）、回饋照片上傳、附件按上傳者分組（寄送證明/回饋照片）、站內對話、未讀數
- **逾期提醒**：手動釋回政策機構的待辦清單（獨立端點與 nav badge）
- **機構設定**：資料維護、承辦人、MANUAL/AUTO 釋回政策與寬限天數
- **年度回顧**：7 張統計卡（含跨年完成、平均完成天數）、每月分布圖（可下鑽單月每日）、認領結果圓餅

### 監控中心（亮色 console）

- **機構審核**：待審清單、核准/駁回（駁回必填理由）、狀態篩選
- **儀表板**：3 張行動導向數字卡 + 4 條分布橫條
- **全站目錄**：跨機構願望（status+年度篩選）與認領（status+overdue 篩選，年度篩選派工中）、認領詳情（附件需明確點擊才載入）
- **稽核軌跡**：5 種敏感動作記錄，對所有管理員公開、敏感列高亮
- **系統**：手動觸發逾期釋回排程
- **年度營運**：平台統計卡、月趨勢下鑽、認領結果分布、機構完成排行 Top 5

### 底層機制（品質亮點）

- 認領狀態機單一收斂點（`Claim.transitionTo`），OCCUPYING 集合與部分唯一索引同步
- 附件三段式上傳（signed URL 直傳 GCS，不經後端）、公私 bucket 分離、私有簽章 10 分鐘
- 隱私採「從不蒐集」策略：孩童無可識別欄位、化名制、View 型別分離
- 逾期自動釋回排程（Cloud Scheduler OIDC 驗證鏈完整）+ 管理端手動觸發（有稽核）
- 年度統計 cohort 制（`TaiwanYear` 單一換算點、台北時區、半開區間）
- 全庫零 TODO/FIXME、註解密度高且說明「為什麼」——但反面是：**缺口都是隱形的，程式碼裡沒有任何標記**

## 2. 缺少的功能（按優先級）

### Tier 1：上線前必要——缺了無法安全營運

| # | 缺口 | 嚴重性說明 |
|---|---|---|
| 1 | **管理端無法停權機構** | `docs/PRIVACY.md:109` 資安事件應變第一步是「立即將機構設為 SUSPENDED」，但 `AdminOrganizationController` 只有 approve/reject——**應變手冊在系統裡執行不了**，只能下 raw SQL。enum、DB 約束、前端篩選選項全都已存在，只缺端點和按鈕，是全專案最便宜的高價值修補 |
| 2 | **零通知機制**（信件/站內推播皆無） | 全系統唯一的信是 Firebase 驗證信。機構**不會知道**願望被認領、捐贈者**不會知道**有回饋照片或新訊息、機構**不會知道**審核結果、沒人會被提醒寄送期限。整個 SHIPPED→RECEIVED→COMPLETED 流程假設雙方主動輪詢網頁。`IMPLEMENTATION_PLAN.md:47` 當初列為「M5 可選延伸」後未再檢視。最低限度：認領成立、審核結果、回饋照片、新訊息、期限前 2 天，共五種信 |
| 3 | **附件無法刪除** | 誤傳的孩童照片（回饋照片敏感度最高）從 UI 永遠刪不掉，直接抵觸隱私手冊的事件處理流程。需附稽核記錄 |
| 4 | **無備份與還原策略** | DEPLOY.md 全文搜「備份」零命中。Neon 誤刪表、壞 migration 都沒有書面恢復路徑；GCS 無版本控制與 lifecycle 規則 |
| 5 | **PENDING 附件孤兒無清理** | 放棄的上傳留下永久孤兒列（可能含 GCS 孤兒物件），沒有 reaper 排程也沒有 lifecycle 規則 |

### Tier 2：營運現實——上線初期就會撞到

| # | 缺口 | 說明 |
|---|---|---|
| 6 | 機構多成員/邀請 | 目前一機構綁一帳號（註冊時 `joinOrganization`），第二位工作人員要手動改 DB |
| 7 | 願望批次操作/CSV 匯入 | 計畫書預估單機構 300–500 個願望，目前一次上架一個、每頁 10 筆 |
| 8 | 管理端內容處置 | 看到願望含孩童真名也無法下架/遮蔽；核准錯的機構不能反悔（`requireAwaitingDecision` 擋掉）；不能介入爭議認領 |
| 9 | Rate limiting | 完全沒有。搶認領尖峰日（計畫書估 15k–75k req/day）唯一防線是 Cloud Run max-instances=10——濫用會變成合法使用者的 DoS |
| 10 | **Swagger UI 在 prod 全開** | `/swagger-ui/**`、`/v3/api-docs/**` 所有 profile 都 `permitAll`，含 admin API 形狀。應限非 prod |
| 11 | 大眾平台關鍵字搜尋與排序 | 願望牆只有三種下拉篩選；**且預設排序是 publishedAt ASC——新願望沉在最後一頁**（見 3.1 bug #4） |
| 12 | 機構主頁 | 捐贈者看不到機構介紹、其他願望、過往紀錄就要決定捐贈 |

### Tier 3：合規與完善

13. 帳號刪除/資料匯出/資料保存政策（訊息、稽核、照片目前全部永久保存，孩童相關照片無到期日）
14. 結構化 JSON log + request ID、錯誤追蹤、uptime 監測、5xx 告警（目前唯一的告警是**帳單**預算）
15. 稽核軌跡的日期篩選/匯出；「誰看過這筆認領」查詢已寫好在 repository 卻沒有端點（死碼）
16. 捐贈者檢舉/回報按鈕；管理端能否看站內對話需要一個明確決策（現在刻意不能，爭議處理時是盲的）
17. 願望收藏/分享按鈕、OG meta（分享願望連結時預覽是通用標題，也沒有 per-page `document.title`——大眾平台全部頁面都沒設，console 反而都有）
18. 上傳進度條與失敗重試（計畫書 M6 明列未做）、上傳前隱私勾選（M4 明列未做，現為被動提示）
19. 給孩子的話寫完後捐贈者自己看不到（`donorMessage` 有回傳但 ClaimDetail 沒渲染）；認領也連不回願望頁（`wishId` 有但沒用）

## 3. 上線後 UX 問題預判

### 3.1 已確認的 bug（建議下一輪就修）

1. **NotFound 頁在深色主題上幾乎看不見**——`NotFound.tsx:9-12` 用亮色主題的深綠/莓紅文字，render 在近黑背景上
2. **Spinner 在深色主題近乎隱形**——`Feedback.tsx:8` 寫死深綠 border，`index.css` 的 `.theme-night` 覆寫獨漏 spinner
3. **願望牆空狀態判斷失效**——`WishWall.tsx:76` 用物件參考相等（`filters === EMPTY_FILTERS`），碰過篩選後永遠不成立，文案誤導
4. **願望牆舊到新排序**——後端 `sort = "publishedAt"` 未指定方向（ASC），新願望在最後一頁，對「上新品」的營運模式是反的
5. **Email 驗證橫幅無深色覆寫**——玻璃主題上一條實心亮黃橫幅（`EmailVerificationBanner.tsx:34`）

### 3.2 操作順暢度

- **翻頁/篩選閃爍**：願望牆與我的認領沒用 `keepPreviousData`（年度頁已用，模式現成），每次翻頁整個列表退回 spinner；翻頁後也**不會捲回頂部**
- **篩選狀態不進 URL**：願望牆的篩選/頁碼是 useState，無法分享、書籤、上一頁還原（機構後台已用 useSearchParams，模式現成）
- **對話體驗**：訊息串不會自動捲到最新（長串開在最舊）、無輪詢（對方回覆要手動刷新才看得到）、送出無樂觀更新（等完整往返）
- **一鍵成立有期限義務的認領**：認領按鈕沒有確認步驟，後果文案在按鈕下方
- **寄送單號打錯無法修改**：只有 POST /ship，沒有更正管道，只能走對話請機構包涵
- **簽章網址過期**：照片簽章 10 分鐘過期，頁面掛著不動照片會變破圖，無自動換簽
- **多處錯誤靜默降級**：附件載入失敗顯示成「還沒上傳」、時間軸錯誤顯示「尚無紀錄」、年度小結錯誤讓年份下拉默默沒選項——使用者會得出錯誤結論
- **機構儀表板五個計數互相等待**：最慢的查詢擋住全部卡片；且用 `size=1` 拿 totalElements 的技巧打五次
- **逾期提醒的行動距離**：文案叫機構「先透過對話聯繫」，但對話藏在展開後的第二層

### 3.3 排版與畫面設計

- **手機版整體薄弱**：大眾平台全部檔案只有 8 個響應式 class；`MyProfile`/`LoginPage`/`PublicLayout`/`MessageThread` 完全沒有斷點。大眾平台 header 靠 flex-wrap，窄螢幕疊三行；console 側欄在 375px 是佔兩三行的水平 chips（無抽屜/漢堡）。**捐贈者大量會用手機**（收到分享連結點開），這是上線後最大的觀感風險
- **無 skeleton**：所有載入都是置中 spinner 取代內容，感知速度差
- **照片格線不響應**：認領詳情 PhotoGrid 固定三欄，手機上約 100px 縮圖
- **結果數量在最需要時消失**：篩到 5 筆（單頁）時 Pagination 整個不渲染，「共 X 筆」跟著消失
- **字數上限無提示**：給孩子的話（500）與訊息（2000）到頂靜默截斷
- 設計系統文件（DESIGN.md）只稽核了大眾平台，三個 console layout 在體系之外

### 3.4 無障礙（上線前至少修高影響項）

- 大眾平台路由檔案 aria-* 幾乎為零；主要內容圖片全部 `alt=""`（願望主圖、回饋照片是內容不是裝飾）
- 表單錯誤沒有 `aria-invalid`/`aria-describedby`；成功通知無 `aria-live`（錯誤有、成功沒有，讀屏使用者聽得到失敗聽不到成功）
- `Button` 元件無可見 focus ring（兩主題皆無）、型別誤標為 `InputHTMLAttributes`
- 無 skip link、路由切換無焦點管理

## 4. 建議處理順序

1. **上線閘門（Tier 1 全部 + Swagger 收口 + 3.1 五個 bug）**——沒有這些不該對外
2. **第一週體感（3.2 的 keepPreviousData/捲頂/URL 狀態 + 3.3 手機版 header/格線）**——便宜且面向最多人
3. **營運量能（Tier 2 的多成員、批次上架、內容處置、rate limiting）**——首個機構大量上架前完成
4. **通知機制做深**（Tier 1 #2 先做五種信，再考慮站內通知中心）
5. **合規與長尾**（Tier 3）

> 計畫書比對：`online-santa-project-plan.md` 的 8 項待辦實際全部完成（勾未打）；`IMPLEMENTATION_PLAN.md` 明列未做的有：Email 通知（M5 可選）、結構化 log（M7）、無限捲動（M6，改用分頁屬合理替代）、401 自動重試（M6，Firebase 自行刷新影響低）、上傳進度條與重試（M6）、隱私勾選（M4）、ADR 文件。
