# 2025 歷史資料移植與帳號激活計畫

> 2026-09-10 · fable-brain · 狀態：待審閱，尚未派工
>
> 目標：把 2025 年活動的實際資料（CSV，欄位與現行 schema 不同）整理匯入新系統；
> 為所有舊用戶建立**無法登入的暫存帳號**；正式啟用時寄激活信，舊用戶點連結接回
> 原帳號，不用重新註冊；今年不參與者不激活，但歷史認領紀錄仍供 admin 檢視。

---

## 1. 架構契合點（為什麼這個設計便宜）

系統現有機制恰好構成這個方案的地基，以下都已核實：

| 需求 | 現成機制 |
|---|---|
| 激活 = 接回舊帳號 | `UserProvisioningService.adoptOrCreate()`：以 UID 找不到帳號時用 email 接手並改綁 UID，**已強制信箱驗證**（防奪帳，`auth/UserProvisioningService.java:59-71`） |
| 暫存帳號無法登入 | 登入身分在 Firebase；匯入帳號在 Firebase 沒有對應帳號，自然登不進，**不需要任何停用機制** |
| `firebase_uid NOT NULL` | 用佔位值 `import-2025-<uuid>`，激活時 `linkFirebaseUid` 換成真 UID，**免 migration**；佔位前綴同時是「未激活」的天然標記 |
| 2025 年度回顧 | cohort 制以 `claimedAt` 歸年——匯入時保留原始時間戳，三種角色的年度統計自動對 2025 成立 |
| 名稱品質 | CSV 有真名就用真名；缺名的帳號激活時會被 `repairLegacyDisplayName` 用 Google name claim 自動修正 |

⚠️ **匯入帳號絕不可設 `disabled=true`**：接手路徑先找到帳號再檢查 disabled，設了會把激活擋死。

## 2. 工作包一：2025 資料匯入（ETL）

### 流程

1. **欄位對映表**：CSV 舊欄位 → 新 schema，逐欄寫明轉換規則（含單位、代碼表、預設值），對映表本身進版控（不含資料）。
2. **轉換腳本**（一次性，不進 Flyway）：CSV → 中繼 SQL。設計成**冪等**（以 email＋舊系統認領編號為自然鍵，重跑不重複建）。
3. **staging 演練**：在 Neon branch（見 BACKUP.md）完整跑一遍，對帳通過才碰正式庫。
4. **對帳清單**：匯入前後筆數（users/organizations/wishes/claims 各表）、認領狀態分布、各月認領數 vs CSV 原始統計，全部要對得上並留存紀錄。
5. **正式匯入**：直灌 SQL。**絕不走應用層 API**——業務流程掛著 AFTER_COMMIT 通知監聽器，走 API 會對 2025 的舊事件亂發通知信。

### 資料規則

- **認領只匯終局狀態**（COMPLETED / RELEASED / CANCELLED）。CLAIMED 會被逾期清單、自動釋回排程、期限提醒信三個機制咬到。
- **時間戳**：CSV 的時間是台北時間，一律轉 UTC 存入；保留原始 `claimedAt` / `completedAt`。日期格式先全檔掃描確認（12/1 與 1/12 的歧義）。
- **`createdAt` 要回填**：使用者與願望的 `createdAt` 若放任 auditing 填成匯入當日，2026 年度統計會出現「新捐贈者/新願望」的巨量假尖峰、2025 年度反而是 0。SQL 匯入直接寫入歷史日期（CSV 有註冊日用註冊日，沒有就用該用戶 2025 首筆認領日）。
- **email 正規化**：lowercase（唯一索引是 `lower(email)`）、trim、剔除格式不合法者（進人工清單）。
- **機構**：一併匯入，status=APPROVED（2025 已審核過的既得信任）；其願望設 FULFILLED/ARCHIVED（不會上牆）。
- **timeline**：匯入認領無 `claim_events`，詳情頁時間軸會顯示「尚無紀錄」——為每筆合成一則「2025 年歷史資料匯入」事件（型別沿用既有 enum 或加註記），避免看起來像資料壞掉。
- **ID 對映表**：舊系統編號 ↔ 新 UUID 的對照要留存（加密保存,見 §5），日後用戶詢問「我去年那筆紀錄」時查得到。

## 3. 工作包二：暫存帳號與激活

- **暫存帳號**：`firebase_uid = 'import-2025-' + uuid`、CSV 真名、email、（若有）電話。role 依 2025 身分（DONOR / ORG_MEMBER＋organizationId）。
- **激活路徑**：激活信連結 → 登入頁（帶說明文案）→ 用戶以同一 email 註冊或 Google 登入 → 信箱驗證 → adoptOrCreate 接手。**激活是引導不是閘門**：用戶沒收到信、自己來註冊同 email 也會接回舊帳號——視為特性（自然激活）；若要硬閘門需 activation token 機制，成本高，不採用。
- **激活信（新功能，需實作）**：
  - 批次寄送：名單來自 `firebase_uid LIKE 'import-2025-%'` 的帳號；每帳號記錄已寄時間（防重寄），admin 端觸發、寫稽核。
  - **分批**：Brevo 免費額度每天 300 封，名單超過就分天寄（排程或人工分批）。
  - 信件內容含：活動開始告知、激活連結、**資料移轉告知**（§5）、退訂/刪除聯絡方式。
- **退訂處理**：回信或連結表達不願參與者，記入排除名單（不再寄信），帳號進入落日流程（§6）。

## 4. 隱性問題清單

1. **CSV 資料品質**：重複 email（同人不同名？取最新）、無效 email、編碼（Big5/UTF-8 先確認）、全半形與空白。ETL 要有「進人工清單」的出口，不要硬塞。
2. **統計語意汙染**（最容易漏）：`createdAt` 不回填會毀掉 2026 年度統計，見 §2。
3. **死信與寄件信譽**：一年前的 email 名單必有失效地址，大量退信會傷 SMTP 帳號信譽，**連帶影響系統所有通知信的送達率**。首批先寄小樣本觀察退信率，並將 Brevo 的 bounce 名單回收為排除名單。
4. **一人多角色**：同一 email 在 2025 既是捐贈者又是機構承辦人——本系統一帳號一角色，需在 ETL 前決定歸屬規則（建議：機構身分優先，捐贈紀錄仍掛同一帳號）。
5. **機構資訊過時**：匯入的機構聯絡資訊可能已變。激活後引導機構到「機構設定」重新確認資料；今年要上架願望前 admin 可抽查。
6. **重跑安全**：正式匯入若中途失敗，冪等設計＋Neon branch 快照讓重跑安全；匯入前先建 branch 當還原點。
7. **激活率的度量**：`import-2025-%` 前綴天然可查——`count(*) where firebase_uid like 'import-2025-%'` 即未激活數，營運隨時可看，也供落日排程使用。
8. **dev 環境汙染**：staging/dev 演練資料演練完即清（branch 直接刪），不留真實個資在測試環境。

## 5. 個資保護規劃（本計畫的核心）

### 5.1 原則

- **資料最小化**：只匯入系統功能需要的欄位——email、顯示名稱、電話（若原本有蒐集）、認領紀錄。CSV 裡其他欄位（地址、生日、任何多餘個資）**一律不匯入**。
- **目的限定**：匯入與寄信屬 2025 蒐集目的（活動聯繫）的自然延續；激活信不得夾帶與活動無關的行銷內容。
- **告知義務**：激活信內明確說明——你的哪些資料被移轉到新系統、用途、保存期限（落日條款）、如何要求立即刪除。這封信同時就是個資法的告知程序。

### 5.2 原始檔案的處置紀律

- CSV 原檔與 ETL 中繼檔**全程加密保存**（至少 zip+密碼或磁碟加密），只放在執行匯入的那台機器。
- **絕不進 git**（`.gitignore` 先加規則擋住 `*.csv` 於資料目錄）、不上傳雲端硬碟、不貼進任何線上工具。
- 對帳完成、確認匯入正確後 **14 天內刪除**原檔與中繼檔（保留對帳統計數字即可，那不含個資）。
- ID 對映表視同個資，同等加密保存，落日後一併刪除。

### 5.3 落日條款（未激活帳號的結局）

- **規則**：本屆活動結束日起算 **3 個月**（待你確認，見 §7）仍未激活的暫存帳號 → **匿名化**。
- **匿名化內容**：`display_name` → 「歷史捐贈者」、`email` → `deleted-<uuid>@removed.invalid`（保持唯一約束成立）、`phone` → null、`firebase_uid` 佔位值保留（永遠不會有人激活它）。
- **保留**：認領紀錄本體（狀態、時間戳、願望關聯）保留——admin 的歷史營運統計不受影響，但再也對應不回自然人，個資風險歸零。機構端看到的 donorName 變成「歷史捐贈者」。
- **實作**：一支排程或 admin 手動觸發的一次性作業（寫稽核）；這套匿名化邏輯**同時就是未來「使用者要求刪除帳號」功能的基礎**（體檢報告 Tier 3 的缺口，一魚兩吃）。
- 已激活的帳號即為現役用戶，適用一般規則，不在落日範圍。

### 5.4 存取與執行紀律

- 正式匯入由誰、何時、從哪台機器執行，記錄於維運筆記；匯入前後的 Neon branch 名稱一併記錄。
- 匯入後在 `docs/PRIVACY.md` 補一節「歷史資料移轉」記錄本次移轉的範圍與法遵依據。

## 6. 建議實作切分（審閱通過後派工）

1. **ETL 腳本 + 對映表 + staging 演練**（不動產品程式碼）
2. **合成 timeline 事件 + createdAt 回填規則**（隨 ETL）
3. **激活信批次功能**：名單查詢、已寄記錄（小 migration：`users.activation_mail_sent_at`）、admin 觸發＋稽核、分批策略
4. **落日匿名化作業**：匿名化邏輯（可複用為帳號刪除）、觸發方式、稽核
5. **PRIVACY.md 增補**

## 7. 待你確認的事項

1. 落日期限：活動結束後 **3 個月**匿名化，可接受？（太短怕誤傷晚回來的人，太長個資躺著沒意義）
2. CSV 實際有哪些欄位？請提供**欄位名稱清單**（不用給資料內容），我來寫對映表初稿。
3. 一人多角色的歸屬規則（§4-4，建議機構身分優先）同意嗎？
4. 2025 的機構是否全數直接 APPROVED？還是今年要上架前需 admin 重新過一次？
5. 舊用戶大約幾人？（決定激活信要不要分批、分幾天）
