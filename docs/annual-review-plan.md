# 年度回顧功能規劃書

> 線上老公公 · 2026-09-01 · 規劃：fable-brain · 待審閱後派工 sonnet-worker

## 1. 背景與目標

平台運作跨年之後，三種角色都需要回顧自己在過去年度做了什麼：捐贈者（DONOR）想看歷年的認領紀錄、機構（ORG_MEMBER）想掌握每年度的認領與完成狀況、管理員（ADMIN）需要各年度的營運全貌。

這是一組**純唯讀的統計與篩選功能**：不動認領狀態機、不改任何寫入流程、不需要資料表結構變更（至多為查詢效能補一個索引）。所有數字都從既有資料即時彙總。

## 2. 「年度」的定義

目前整個系統沒有任何年度、檔期概念（已全面查證），時間一律以 UTC `timestamptz` 儲存。年度歸檔必須先定義兩件事：

> **決策一：年度 = 台灣時區（Asia/Taipei）的日曆年**，1 月 1 日至 12 月 31 日。後端新增單一的 `ZoneId` 常數與「年度 → 半開 Instant 區間」工具（2025 年即 `[2024-12-31T16:00Z, 2025-12-31T16:00Z)`），所有統計查詢共用，避免各處自算造成邊界不一。

> **決策二：認領的年度以 `claimedAt` 一次定錨（cohort 制）。**一筆認領的完成、釋回、取消都歸屬「認領那一年」——12/20 認領、隔年 1/10 完成的禮物，整筆算在認領年度。這解決聖誕檔期作業跨年末的問題：年末認領就是該屆聖誕的成果，不會被日曆切成兩半。`claimedAt` 為 NOT NULL、建立後不可變、且已有索引，是最可靠的歸檔鍵。願望以 `createdAt` 歸年、新註冊使用者與機構以 `createdAt` 歸年。
>
> cohort 制的特性：**近年度的數字會隨進行中的認領逐漸收斂**（去年 12 月的認領在今年 1 月完成時，去年的完成率會上升）。年度頁面需標註「進行中認領完成後，數字將更新」之類的說明，避免誤解。

⚠️ **陷阱：不能用 `Wish.publishedAt` 統計「該年發布的願望」。**已下架的願望重新上架時會沿用第一次發布的時間戳（`Wish.java` 的 `publish()` 只在為空時寫入），機構若回收願望重用，數字會歸錯年。

前端顯示年度標籤與年度統計時，日期格式化需固定 `timeZone: 'Asia/Taipei'`——現況是跟著瀏覽器時區走，人在海外的捐贈者會看到「12/31 的認領被歸進隔年」的錯位。既有的一般日期顯示維持不變，只有年度相關頁面加此設定。

## 3. 各角色功能

### DONOR — 我的認領：年度篩選與年度小結

- 「我的認領」頁加**年度下拉篩選**（全部／2026／2025⋯，選項由後端回傳實際有資料的年份）。
- 選定年度時，清單上方顯示**年度小結卡**：該年認領 N 筆、完成 M 筆、送出禮物給 X 位孩子、支持了 Y 間機構。深色玻璃主題，沿用共用元件。

### ORG_MEMBER — 機構後台：年度回顧頁

- 機構後台新增導覽項「年度回顧」（`/org/annual`），年度選擇器放在面板右上角的 action 插槽。
- **統計卡**：該年新增願望、被認領、完成、完成率、釋回、取消、逾期自動釋回次數、平均完成天數（claimedAt → completedAt）、**跨年完成**（該年度認領、隔年才完成的筆數，量化年末作業拖尾）。
- **每月認領分布**與**認領結果圓餅**：用 Recharts 繪製（見第 4 節）。

### ADMIN — 監控中心：年度營運頁

- 監控中心新增導覽項「年度營運」（`/admin/annual`）。
- **平台統計卡**：新註冊捐贈者、活躍捐贈者（該年至少一筆認領）、新加入機構、發布願望、認領、完成、平台完成率。
- **每月認領趨勢**（長條圖）與**認領結果分布**（完成／釋回／取消，圓餅或環圈圖），用 Recharts 繪製。
- **機構完成排行**：該年完成認領數前五名的機構（橫向長條圖），僅管理端可見，機構彼此看不到對方數字。

## 4. API 設計

| 端點 | 說明 |
|---|---|
| `GET /api/claims/me?year=` | 既有清單端點加選填年度參數，用 JPQL nullable-filter 既有模式（比照 `WishRepository.search()`）。 |
| `GET /api/claims/me/annual-summary?year=` | 捐贈者年度小結 + 可選年份清單。 |
| `GET /api/organizations/me/stats/annual?year=` | 機構年度統計。 |
| `GET /api/admin/stats/annual?year=` | 平台年度統計（比照既有 `/api/admin/stats` 的 Service 結構）。 |

⚠️ **安全注意**：`/api/organizations/me/**` 沒有路徑層級的角色限制，全靠 Service 呼叫 `requireOrganizationId()` 擋人。新的機構統計端點必須走同一個方法，否則任何登入者都打得到。管理端點則沿用 `/api/admin/**` 的雙重防護。

- 每個 annual 端點回應附 `availableYears`（由最早一筆 `claimedAt` 推導），前端下拉選單直接用，不寫死年份。
- 每月分布需要 native query 的 `date_trunc('month', claimed_at AT TIME ZONE 'Asia/Taipei')`（JPQL 表達不了時區轉換；repo 已有 native query 前例）。其餘彙總比照 `AdminStatsService` 的 GROUP BY + 補零 helper 模式。cohort 制下完成數等指標一律以 `claimedAt` 落在年度區間為 WHERE 條件，再按 status 分組，不用 `completedAt` 篩年。
- 無 migration。若機構端統計實測偏慢，允許加 V5 補 `(organization_id, claimed_at)` 索引，由實作時判斷。

### 圖表函式庫

- 引入 **Recharts**（React 生態最通行的宣告式圖表庫，支援 React 19），取代原規劃的手刻 CSS 橫條圖——現有監控儀表板過於單調，年度頁面用正式圖表提升專業度。
- 只用於機構「年度回顧」與管理「年度營運」兩頁（亮色主題）；大眾平台的捐贈者小結卡維持數字卡形式，不上圖表。
- 兩個年度頁用 `React.lazy` 切分載入，避免 Recharts 進入大眾平台的首頁 bundle。
- 圖表配色沿用專案既有的 Tailwind token 色系，與 console 亮色主題一致。
- 既有 AdminDashboard 的手刻橫條圖是否也換成 Recharts：**本次不動**，留待年度頁驗證效果後另開任務。

## 5. 派工切分

一次派工、建議三個 commit，方便逐段審查：

1. **後端**：年度區間工具、三個統計端點、`listMine` 年度參數，含整合測試。
2. **Console 前端**：機構「年度回顧」與管理「年度營運」兩頁（亮色主題，複用現有 Headline／Distribution／ConsolePanel 模式）。
3. **大眾平台前端**：「我的認領」年度篩選與小結卡（深色玻璃主題）。

## 6. 驗收條件

- 統計端點整合測試須涵蓋**年度邊界**（台北 12/31 23:30 的認領屬當年、UTC 已是隔年）與**機構隔離**（A 機構看不到 B 機構的數字）。
- `mvn test`、前端 build 與 lint 全過；Playwright 走查三個角色的頁面。
- 統計數字與手動建立的測資對得上（測試內以固定 Instant 建資料驗證）。

## 7. 已確認決策（2026-09-01 審閱）

1. **年度 = 台北日曆年，認領以 `claimedAt` 定錨（cohort 制）**：跨年末的作業（年末認領、隔年初完成）整筆歸認領年度，另設「跨年完成」統計卡量化拖尾規模。
2. **機構完成排行僅管理端可見**，機構彼此看不到對方數字。
3. **引入 Recharts** 繪製年度頁圖表，僅限兩個 console 年度頁並 lazy 載入；既有儀表板本次不動。
